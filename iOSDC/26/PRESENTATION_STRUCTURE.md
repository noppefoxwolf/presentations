# `presentation-draft-2.md` 構成分析

## 発表全体の目的

この発表は、画面サイズやデバイスごとの見た目を個別に作るのではなく、変わらない目的を定め、環境に合う見せ方を選ぶルールとしてUIを設計・実装する考え方を伝える。

全体を一文で表すと、次のようになる。

> 画面サイズごとの見た目を個別に作るのではなく、変わらない目的を定め、環境に合う見せ方を選ぶルールとして実装する。

## スライドの表示ルール

- タイトルだけ：表紙、番号付きの章・節の入口、最後の結論
- タイトルと本文：通常の説明
- 画像だけ：画面例

章見出しと、その章で最初に扱う内容は同じスライドへ載せない。章の入口で現在地を示し、次のスライドから具体的な内容へ進む。

## 一番大きな構成

1. どの部分が使いにくくなったか
2. このUIで、ユーザーは何をしたいか
3. レイアウトを調整するか、構成を変えるか
4. 環境ごとの違いをどこで吸収するか
5. 判断手順を持ち帰る

流れを図にすると、次のようになる。

```text
使いにくさを発見する
        ↓
変えない目的を定める
        ↓
必要な変更の大きさを選ぶ
        ↓
選択ルールとして実装する
        ↓
次の未知の環境にも適用する
```

章番号に対応させると、第1章と第2章が判断基準づくり、第3章が具体的な適応、第4章が実装設計にあたる。導入と結論が、それらを問題提起と持ち帰れる手順で挟んでいる。

## 導入：なぜ柔軟なUIが必要なのか

導入は、次の順番で進む。

```text
具体的な違和感
→ 隠れていた前提
→ 変わらないもの／環境に合わせて変えるもの
→ 今日扱う判断の全体像
```

### 1. 広い画面で違和感を見せる

iPhone向けのニュース画面を広いウインドウに表示する。画面は壊れていないが、余白が増え、広さを活かせていない。

目的は、「マルチデバイス対応」という抽象的な話ではなく、聴衆が見て分かる使いにくさから始めることにある。

### 2. 画面に埋め込まれた前提を発見する

違和感の原因を、「一覧が一列になる前提だった」と言語化する。

これによって、問題は単なる余白ではなく、狭い環境を前提にした構成をそのまま広げたことだと示す。

### 3. 変わらないものと環境に合わせて変えるものを分ける

記事、ユーザーができること、選択や保存の状態は変えない。一方で、情報量、レイアウト、操作方法は環境に合わせて変える。

ここで、この発表全体を支える原則を先に置いている。

### 4. 発表全体の判断手順を予告する

「今日持ち帰る4つの判断」で、その後の章を案内する。

1. 使いにくさを特定する
2. ユーザーの目的を確認する
3. レイアウト調整か構成変更かを選ぶ
4. 違いを吸収する実装場所を決める

この4項目が、そのまま第1章から第4章へ対応している。

## 第1章：どの部分が使いにくくなったか

この章は、次の構成になっている。

```text
ユーザーに起きる具体的な問題
→ 問題の分類
→ 問題ごとに異なる解決策
```

### Case 1：記事を見分ける情報が欠ける

Dynamic Typeやローカライズで文字量が増え、記事を識別するための情報や操作が欠ける問題を示す。

- 見出しの途中が切れる
- 記事同士を区別できない
- 保存などの操作が押し出される

文字が増えることは原因であり、使いにくさは記事を見分けたり操作したりできなくなることにある。

### Case 2：一覧で記事を比較できない

広いウインドウでカードだけが横へ伸びても、一度に見える記事は増えず、一覧と詳細の往復も残る。

空間が広がることは原因であり、使いにくさは記事を比較しやすくならないことにある。

### Case 3：同じ記事の情報がまとまって見えない

縦横比が変わると、画像、見出し、補助情報が離れ、一つの記事として認識しにくくなる。

向きが変わることは原因であり、使いにくさは関連する情報のまとまりが弱くなることにある。

### 4. 問題と解決策を対応させる

最後に、問題を分類して選択肢へ結び付ける。

| 問題 | 主な対応 |
|---|---|
| 内容が収まらない | セルフサイジング、スクロール |
| 情報密度が低い | 最大幅、複数カラム |
| 内部配置が窮屈 | 縦横配置の切り替え |
| 情報の関係が弱い | UIの構成変更 |

この章の着地点は、「適応」という一つの言葉でまとめず、起きている問題の種類を先に見極めることにある。

ここから、第2章の「何を基準に解決方法を選ぶのか」へ進む。

## 第2章：このUIで、ユーザーは何をしたいか

この章は、次の構成になっている。

```text
ユーザーの目的
→ UIを決める条件
→ 共通部分の定義
→ コンポーネントへの分解
→ 情報の優先順位
→ 複数の見せ方
```

第2章の目的は、見た目を変えるときの判断基準を、モデルとユースケースから作ることにある。

### 1. ニュースアプリのユースケースを確認する

ニュースアプリでユーザーがしたいことを、次のように定義する。

- 記事を見つける
- 読むか判断する
- 記事を読む
- 保存する

ここで、デッキ全体を通して使用するニュースアプリの具体例を固定する。

### 2. UIを決める3条件を示す

```text
表示されるUI
= 意味 × コンテナ × 環境
```

- 意味：何を表し、何ができるか
- コンテナ：実際に利用できる領域
- 環境：プラットフォーム、入力方法、文字サイズ

目的は、UIを端末名だけで決めないことにある。同じiPadでも、ウインドウやペインの幅によって、コンポーネントが利用できる領域は異なる。

### 3. 共通するものを先に決める

共通にするものと、環境に合わせるものを分ける。

| どの環境でも共通 | 環境に合わせて変える |
|---|---|
| Articleモデル | カード、リスト、詳細ペイン |
| 記事を探して読むこと | 一列、グリッド、複数カラム |
| 記事を保存できること | タップ、ポインタ、キーボード |

これによって、環境ごとに別のArticleや別のユースケースを作るのではないと明確にする。

### 4. 画面を役割のある単位へ分解する

ニュース一覧を、ArticleやFilterなどの部品として捉え直す。

さらにUIを、次の3つの粒度に分ける。

```text
画面フロー
→ 画面
→ コンポーネント
```

目的は、何を組み替え、何を再利用するのかを判断できるようにすることにある。

### 5. コンポーネントの境界を役割から決める

コンポーネントを単なる画面上の矩形ではなく、次の観点で切り分ける。

- 何を表すか
- ユーザーが何をしたいか
- 別の画面でも同じ役割を持つか

Articleは「画像とテキストの箱」ではなく、「記事を識別し、読むか判断し、詳細へ進むための単位」として定義される。

### 6. モデルから見た目の情報を外す

Articleモデルには記事そのものの情報を持たせ、`imageWidth`や`titleLines`などの表示情報は持たせない。

これにより、同じArticleをカード、詳細画面、Widgetなどで使えるようにする。

### 7. ユースケースから情報の優先順位を決める

記事を識別する、読むか判断する、開く、保存するという目的に対して、必要な情報を対応させる。

狭い場所で何を省くかを、余白の都合ではなく「省いた結果、何ができなくなるか」から決める。

### 8. 複数の見せ方を用意する

共通のArticleに対して、Compact、Regular、Wideなど、情報量の異なる表現を用意する。

Compactは「iPhone版」ではなく、狭いコンテナに適した見せ方として扱う。特定の端末と表示バリエーションを一対一に固定しないことが重要になる。

### 9. デザインデータの読み方へ広げる

デザインデータを、すべての環境で守る座標ではなく、「特定のコンテンツ、コンテナ、環境における完成例」として扱う。

別の環境では座標を再現するのではなく、情報の優先順位や、要素同士を近づけた理由を引き継ぐ。

### 10. AIを分析の補助として位置付ける

最後に、既存画面から対象や操作のまとまりを見つける作業を、AIで補助できると紹介する。

ただし、プロダクトとして何をモデルとし、どのユースケースを優先するかはチームが判断する。

この章の着地点は、UIを変える前に、変えないArticleとユースケースを定義することにある。

## 第3章：レイアウトを調整するか、構成を変えるか

第3章は、大きく二つに分かれている。

```text
3.1 同じ構成のまま調整する
3.2 調整だけでは足りない場合に構成を変える
```

これは発表の中心となる対比である。

### 3.1 同じ構成のまま幅に合わせる

内部構成は次のようになっている。

```text
広い空間の使い方
→ 一覧全体の列数
→ カード内部の配置
→ APIの役割と限界
→ 連続適応の適用範囲
```

#### 広い空間をどう使うか選ぶ

広いからすべてを引き伸ばすのではなく、コンテンツの役割に応じて選ぶ。

- 本文なら最大幅を設ける
- 一覧なら列数を増やす
- 必要なら補助領域を置く

目的は、余白を埋めることではなく、ユーザーの作業を改善することにある。

#### グリッドの列数を内容から決める

ニュース一覧では、カードを伸ばさずに列数を増やす。

列数は「iPadなら三列」のような端末名ではなく、カードを読める最小幅から決める。

#### 最小幅も固定的ではないと示す

カードに必要な幅は、次の条件によって変わる。

- 文字サイズ
- ローカライズ
- 情報量
- 操作領域

ブレークポイントもデザイン上の絶対値ではなく、読みやすさを守る制約として扱う。

#### コンポーネント内部の配置を切り替える

同じArticleでも、広いときは横並び、狭いときは縦並びにする。

カード自身が、親から渡された幅に収まる配置を選ぶ構造にする。

#### `ViewThatFits`の使い方と限界を示す

`ViewThatFits`は収まる候補を選べるが、次のことまでは決めない。

- どの情報を残すか
- どの配置を優先するか
- どの候補を用意するか

ユースケースから候補を設計したうえで、収まりの判定だけをAPIへ任せる。

#### 余白とあふれを再確認する

第1章で分けた問題へ戻り、次のように整理する。

- 余白には最大幅やグリッドを使う
- あふれにはセルフサイジングやスクロールを使う

#### 連続適応の適用範囲をまとめる

最後に、構成を変えずに調整できるものをまとめる。

- 余白と最大幅
- 折り返しと高さ
- グリッドの列数
- コンポーネント内部の配置

これで操作上の問題が解決しない場合は、構成変更へ進む。

### 3.2 レイアウト調整で足りなければ構成を変える

内部構成は次のようになっている。

```text
レイアウト調整の限界
→ 構成変更の具体例
→ 2種類の変更の比較
→ 切り替える条件
→ 役割を表すシステムAPI
→ 別の表示場所への展開
```

#### レイアウト調整では解決できない問題を示す

一覧のカード幅を調整しても、次の往復は減らない。

```text
一覧 → 詳細 → 戻る → 一覧 → 詳細
```

ここで、問題が要素のサイズではなく、画面同士の組み合わせにあると示す。

#### 一覧と詳細を同時表示する例を見せる

狭い環境では一つの内容へ集中し、広い環境ではサイドバー、一覧、詳細を同時に見せる。

広い側を上位版として扱わず、狭い側と広い側を、それぞれ異なる条件に適した構成として扱う。

#### レイアウト調整と構成変更を比較する

| レイアウト調整 | 構成変更 |
|---|---|
| 画面の役割は変えない | 画面の組み合わせを変える |
| 連続的に変化する | 境目で切り替える |
| 列数、余白、内部配置 | ナビゲーション、ペイン |

ここで二つの違いを明確に言語化する。

#### 構成を変える条件を定義する

構成変更は「iPadだから」ではなく、次のようなユーザーの作業から判断する。

- 一覧と詳細を同時に見たい
- 往復が作業を妨げている
- 主要な行き先が増えた
- 補助情報を見ながら作業したい

#### 役割を表すSwiftUI APIへ接続する

続いて、SwiftUIのAPIを役割ごとに紹介する。

- `TabView`：主要な行き先
- `NavigationSplitView`：選択と詳細
- `Inspector`：現在の内容を補う情報

先にAPIを紹介するのではなく、構成変更の必要性と役割を定義してから、その役割を表せるAPIへ接続している。

#### WidgetやWatchへ話を広げる

最後に、同じArticleをiPhone、広いウインドウ、Widget、Watchで見せる例へ広げる。

ここでは、小さい画面を大きい画面の縮小版として扱わない。場所が変わればユースケースも変わり、必要な情報の選び方も変わる。

この節によって、「ウインドウ幅への対応」だった話が、「異なるデバイスや表示場所への展開」へ広がる。

## 第4章：環境ごとの違いをどこで吸収するか

この章の構成は次のようになっている。

```text
実装の責任分担
→ 表示候補の定義
→ 呼び出し側のAPI設計
→ 見せ方を選ぶ場所
→ システムAPIへの役割の伝達
→ 共通化する範囲
→ 検証方法
```

目的は、第3章で作った判断を、画面ごとの条件分岐にせず維持できる実装へ変えることにある。

### 1. 実装を4つの層に分ける

```text
モデル
↓
表示バリエーション
↓
レイアウトと構成の選択
↓
プラットフォームの表現
```

まず、どこが何を判断するのかを分離する。

### 2. 同じArticleから複数の表示候補を作る

Compact、Regular、WideのViewは異なる見た目を持つが、受け取るArticleは共通である。

見た目のコードを無理に一つへ統合するのではなく、対象とユースケースを共通にするという考え方を示す。

### 3. 呼び出し側には意味や用途を渡す

呼び出し側は、次のような情報を渡す。

- `article`
- `prominence`
- `purpose`

画像幅や余白ではなく、この記事を目立たせたい、比較して選ぶ場面である、といった意味を渡す設計にする。

### 4. 悪い対比として見た目を渡すAPIを示す

画像サイズ、行数、余白、横並びかどうかを呼び出し側から渡す例を出す。

見た目を渡すと、環境ごとの正解をすべての呼び出し側が知ることになる。この対比によって、意味を渡すAPIが必要な理由を理解させる。

### 5. 見せ方の選択をArticleViewへ集める

`ArticleView`の中で、Wide、Regular、Compactから適切な候補を選ぶ。

新しい環境が増えたときに、利用している画面をすべて修正するのではなく、この選択ルールを拡張できる形にする。

### 6. システムAPIにも位置ではなく役割を渡す

Inspectorの例では、「右側に置く」と指定するのではなく、「現在の内容を補う情報」として宣言する。

プラットフォームに合った位置や表現はシステムへ任せる。

### 7. 共通化する範囲を決める

最後に、何でも共通化すればよいわけではないと整理する。

| 共通化する | 無理に共通化しない |
|---|---|
| モデル | 役割の違うコンポーネント |
| ユースケース | 環境固有の操作 |
| 情報の優先順位 | 偶然同じピクセル値 |
| 選択ルール | すべての見た目 |

この部分は、章の冒頭にある「すべての環境を一つの巨大なAdaptiveViewへ詰め込まない」という話への回答になっている。

### 8. 変化の途中を検証する

最後に、実装した柔軟性を次の条件で検証する。

- 最小幅から最大幅までのリサイズ
- Dynamic Type
- 縦向きと横向き
- タッチ、ポインタ、キーボード

代表的な端末の静止画だけではなく、環境が変化する途中を確認する。

これにより、設計論だけで終わらず、実装後の検証までを一連の工程として閉じている。

## 結論：次の環境でも使える判断手順へ圧縮する

結論は次の構成になっている。

```text
導入と同じ4つの質問を回収
→ 発表全体の主張を再提示
```

導入で予告した判断を、同じ順番の4つの質問として回収する。

1. どの部分が使いにくくなったか
2. このUIで、ユーザーは何をしたいか
3. レイアウトを調整するか、構成を変えるか
4. 環境ごとの違いをどこで吸収するか

そして最後に、次の主張へ戻る。

> 環境ごとの画面を作るのではなく、環境に応じて見せ方を選ぶルールを作る。

### 結論

この構成分析と`presentation-draft-2.md`の間に、大きな内容上の矛盾はない。構成分析はデッキに含まれる内容と順序を概ね正しく表している。

一方で、デッキには、聴衆が章構成を追うときに境界や現在地を見失いやすい箇所がある。主な問題は、章タイトルが約束する範囲と実際の内容の広さ、予告と回収の距離、導入と結論で示す判断項目の違いにある。

### 1. 第2章のタイトルより実際の内容が広い

第2章の入口は「ニュースアプリでユーザーがしたいこと」だが、章内ではUIを決める条件、共通部分、画面の粒度、Articleモデル、情報の優先順位、表示バリエーション、デザインデータ、AIまで扱う。

すべて「ユーザーがしたいことを基準にする」という論旨にはつながっているが、表示される章タイトルからはユースケースの説明だけを予想しやすい。章後半で現在地を見失う可能性がある。

第2章の仕事は、次のように明示すると理解しやすい。

> 変えないArticleとユースケースを決め、見せ方を変えるための部品と優先順位を用意する。

必要なら、章内を次の中テーマに分けられる。

```text
2.1 変えない目的を決める
2.2 画面を役割のある部品に分ける
2.3 目的から表示バリエーションを作る
```

### 2. 「適応には2種類ある」の予告と回収が離れている

このスライドは第3章全体の重要な予告だが、現在は第2章の前半にある。その直後は二種類の適応の詳説ではなく、画面の分解やArticleモデルへ進み、詳説は第3章まで待つ。

論理的には「二種類の適応を実装するため、画面を組み替えられる単位へ分ける」と接続している。ただし聴衆には、このスライドが第3章の予告なのか、直後の画面分解の理由なのかが伝わりにくい。後者であることを遷移で明確にする必要がある。

### 3. 第2章の終盤にAIが一枚だけ現れる

第2章はArticle、ユースケース、情報の優先順位、表示バリエーションを積み上げている。その最後にAI活用が一枚だけ入り、章末のまとめとしては働いていない。

内容自体は役割の洗い出しに関係しているが、発表の中心から別の話題へ移ったように見えやすい。残すなら、第2章の主要ステップではなく、分析作業を助ける補足例だと明示した方がよい。

### 4. 第3章の入口が二段階になっている

「3. Articleとユースケースを基準に見せ方を変える」と「3.1 同じ構成のまま幅に合わせる」が連続している。階層としては正しいが、似た案内が連続しているようにも感じられる。

大章の入口では、第3章全体が次の二つを比較する章だと明示すると役割が分かれる。

```text
同じ構成のまま調整する
        または
画面の組み合わせから変える
```

そのうえで3.1では前者だけへ焦点を絞る。

### 5. 第3章後半でWidget・Watchへ急に広がる

3.2では一覧と詳細、TabView、NavigationSplitViewなど、主にウインドウ内の構成変更を扱う。その後、WidgetやWatchを含む表示場所の違いへ広がる。

内容上の矛盾はなく、「同じArticleでも場所ごとにユースケースが変わる」という重要な補強である。ただし3.2の主題とは少し軸が異なるため、ウインドウ幅の話から別の表示場所へ応用範囲を広げる箇所だと、短い遷移で明示する必要がある。

### 6. Inspectorの概念説明とコード例が別の章にある

第3章ではInspectorを「現在の内容を補う情報」として役割一覧に含め、具体的なコード例は第4章に置いている。

構成を考える章と実装責任を考える章を分ける意図として説明できる。一方、TabViewとNavigationSplitViewは第3章でコード例まで示すため、Inspectorだけ説明が後ろへ送られたようにも見える。

第4章の例が未説明APIの補足ではなく、「呼び出し側は位置ではなく役割を渡す」というAPI設計の例であることを強く示す必要がある。

### 7. 導入の「4つの判断」が結論では「3つの質問」になる

導入では次の4項目を提示する。

1. どの部分が使いにくくなったか
2. このUIで、ユーザーは何をしたいか
3. レイアウトを調整するか、構成を変えるか
4. 環境ごとの違いをどこで吸収するか

結論では次の3項目になる。

1. このUIで、ユーザーは何をしたいか
2. レイアウトを調整するか、構成を変えるか
3. APIから見た目の詳細が漏れていないか

第4項目は具体化されているが、第1項目の「どこが使いにくくなったか」は最終3問から外れる。直前の「実装前の確認」には残っているものの、冒頭で4つを持ち帰ると約束しているため、同じ手順の要約なのか、別用途のリストなのかが分かりにくい。

これは構成上、最も明確な不一致である。冒頭と結論で同じ数と順番を使うか、「実装前には4点、迷ったときは3問」のように用途の違いを明示する必要がある。

### 8. 結論が三段階あり、まとめが重複して見える

終盤には「実装前の確認」「3つの質問」「環境に応じて見せ方を選ぶルールを作る」が続く。それぞれに役割はあるが、内容が近く、まとめが複数回繰り返されているように感じられる可能性がある。

三枚を残すなら、役割を次のように明確に分ける。

- 「実装前の確認」：チームで使うレビュー項目
- 「3つの質問」：個人が覚えて帰る判断手順
- 最終スライド：発表全体を一文で閉じる

### 聴衆に構成を伝えるための優先改善点

優先度が高い順に並べると、次のようになる。

1. 導入の4判断と結論の3質問を揃える、または用途の違いを説明する
2. 第2章を中テーマに分け、ユースケースからモデル・部品・表示バリエーションへ進む流れを見せる
3. 第3章の入口で「レイアウト調整／構成変更」の二部構成を明示する
4. Widget・Watchへの展開を、応用範囲を広げる箇所として案内する
5. AIスライドを補足として位置付け、第2章の結論を弱めないようにする
6. 終盤三枚の役割を分け、同じまとめの反復に見えないようにする

構成の骨格自体を作り直す必要はない。現在の論理は通っているため、章の入口、中テーマへの遷移、章末の回収を明確にすることが、聴衆の理解を改善する最も小さく効果的な変更になる。
